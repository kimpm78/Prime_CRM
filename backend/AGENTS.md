# バックエンド向けエージェント指示

## アーキテクチャと規約

- 本指示は、`backend/` 配下のファイルに対してリポジトリルートの `AGENTS.md` を補足する。
- Laravel 13およびPHP 8.3の規約を使用する。既存のPSR-12スタイルに合わせ、周辺コードで使用されている場合は戻り値の型を明示する。
- コントローラーはHTTP処理の調整に集中させる。再利用可能なバリデーションはForm Requestクラス、永続化に関する動作はモデルまたは責務を限定したサービス、シリアライズは周辺機能で採用されている場合にAPI Resourceへ配置する。
- Eloquentのリレーション、スコープ、Eager Loading、パラメータバインディングを優先する。N+1クエリを避け、信頼できない値をSQLへ直接埋め込まない。
- 1つの業務操作で監査ログを含む複数の関連レコードを書き込む場合は、データベーストランザクションを使用する。
- 日本語利用者向けの既存エンドポイントでは、バリデーションメッセージとレスポンスメッセージを日本語で維持する。

## CRMの動作

- `accounts` は `is_deleted` フラグで論理削除する。通常の取得処理では論理削除済みの取引先を除外し、削除処理で物理削除しない。
- 取引先の登録、更新、削除では、同じトランザクション内で適切な `activity_logs` レコードを引き続き記録する。
- クライアントが制御できるすべてのフィールドをサーバー側で検証する。`fillable`、casts、リクエストルール、データベース制約、APIテストの整合性を維持する。
- 一覧エンドポイントを追加または変更する際はページネーションを維持し、サーバー側で妥当な上限を設定する。
- 内部例外、秘密情報、不要なデータベースフィールドをAPIレスポンスに含めない。

## データベース変更

- スキーマ変更には新しいマイグレーションを作成し、可能な場合は安全な `down()` 処理を用意する。
- 本番環境のPostgreSQLとテスト環境のSQLiteの動作を考慮する。テスト済みの代替手段または文書化された理由なしに、特定データベース専用の構文へ依存しない。
- 新しい外部キー、およびデータ特性上必要な重要フィルターや並び替えに使用するカラムにはインデックスを追加する。
- スキーマまたは必須業務項目を変更した場合は、FactoryまたはSeederとFeatureテストを更新する。

## テストと品質確認

- エンドポイントの動作、バリデーション、必要な場合の認可、データベース副作用、論理削除、監査ログについてFeatureテストを追加または更新する。
- 開発用PostgreSQLを変更しないように、バックエンドテストは次のコマンドで実行する。

```bash
docker compose exec \
  -e APP_ENV=testing \
  -e DB_CONNECTION=sqlite \
  -e DB_DATABASE=:memory: \
  backend php artisan test
```

- Dockerを利用できず、ローカルにPHP依存パッケージが存在する場合は、`backend/` から同じテスト用データベース環境を指定して同等のコマンドを実行する。
- Laravel Pintを利用できる場合は変更したPHPファイルに対して実行し、フォーマット変更を採用する前に差分を確認する。
